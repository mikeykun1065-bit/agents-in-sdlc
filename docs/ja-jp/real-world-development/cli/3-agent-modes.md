最初に小さな機能をプロジェクトに追加しました。より大きな変更には、堅実なプロセスが必要です。GitHub Copilot CLI は組織の既存の開発フローに沿って動作し、適切な方法で必要な機能を構築できます。このレッスンから数回にわたり、issue を起点に機能を追加し、コードを検証し、動作を確認して、プロジェクトにマージするまでの一般的なエージェント主導の開発プロセスを進めます。

> [!NOTE]
> 機能のワークフローでは、同じ会話とブランチを使います。通常、ファイルの種類ごとにブランチや PR を分けますが、ここでは主な概念に集中するため簡略化しています。

このレッスンでは、次のことを行います。

- GitHub issue から Copilot の会話を開始します。
- Plan モードで要件を定義します。
- Autopilot モードで機能を実装します。
- コードをレビューします。
- 転送したブラウザーで手動で機能を検証します。

この後、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して、QA エージェントを作成してから機能 PR を開きます。

## シナリオ

Tailspin Toys のカタログは拡大しており、訪問者はカテゴリや発行元でゲームを絞り込む必要があります。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意する詳細があります。Plan モードで仕様を決めてから、範囲を明確にして Autopilot に実装を許可します。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。むしろ、より重要になります。一般的な開発フローは次のとおりです。

1. 作業内容を記述した登録済みの issue から始めます。
2. 構築する内容を計画します。
3. コードを構築してレビューします。
4. テストを実行して検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードのレビューと継続的インテグレーションが成功したら、マージします。

> [!NOTE]
> 詳細はチームや組織によって異なりますが、ほとんどの場合は上記の流れを調整したものです。

この標準的な手順に従うことで、AI が生成したコードが要件を満たし、手書きのコードと同じレビューと検証を受けるようにできます。

## 会話モード

**会話モード**は、エージェントにどの程度の自律性を与えるかを制御します。<kbd>Shift</kbd>+<kbd>Tab</kbd> でモードを切り替えます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次の操作の前に入力を待ちます。
- **Plan**: エージェントが先に計画を作成します。プロジェクト ファイルの編集はできません。
- **Autopilot**: エージェントがコードの作成、テスト、反復を自律的に進め、タスクを完了します。

まず Plan モードで計画をレビューしてから、Autopilot で実装します。

## issue から始める

フィルター作業を始める前に Codespace に戻り、リポジトリとターミナルの準備を確認します。

1. Codespace に戻ります。停止している場合は再起動します。
2. 星評価の PR がマージ済みであることを確認します。
3. ターミナルが開いていない場合は、<kbd>Control</kbd>+<kbd>\`</kbd> (Mac) または <kbd>Ctrl</kbd>+<kbd>\`</kbd> (Windows/Linux) を押します。
4. `main` を更新し、フィルター作業用のブランチを作成します。

   ```bash
   git checkout main
   git pull --ff-only
   git checkout -b game-filters-cli
   ```

5. Copilot CLI を起動します。

   ```bash
   copilot --yolo
   ```

6. <kbd>Tab</kbd> を 2 回押して **Issues** タブを開きます。
7. <kbd>A</kbd> を押してすべての issue を表示します。
8. 矢印キーで **Allow users to filter games by category and publisher** というタイトルの issue を選択します。
9. <kbd>C</kbd> を押して issue をプロンプトに追加し、**Session** タブに戻ります。

プロンプトは `#7` (または同様の番号) で始まります。`#` を使うと、GitHub 上の issue やプルリクエストを会話のコンテキストに追加できます。

## フィルター機能を計画する

計画を作ると、機能やタスクを Copilot に任せる前に実装方針を決められます。複雑な作業では、事前に計画することをお勧めします。Plan モードに切り替えて計画を作成します。

1. <kbd>Shift</kbd>+<kbd>Tab</kbd> を押して Plan モードに切り替えます。プロンプトの下に **Plan** と表示されていることを確認します。
2. 先ほど追加した issue の参照に続けて、次のプロンプトを入力します。

   ```plaintext
   この機能を実装する計画を作成してください。
   ```

Copilot はプロジェクトを調べて、最適な方法を検討しながら計画を作成します。

3. フィルター機能の動作について質問された場合は、好みに応じて回答します。決まった正解はありません。
4. 計画が完成したら、<kbd>Control</kbd>+<kbd>E</kbd> (Mac) または <kbd>Ctrl</kbd>+<kbd>E</kbd> (Windows/Linux) を押して計画を展開します。
5. 計画を読みます。
6. 決定した内容と異なる部分があれば、Copilot に修正を依頼します。

## Autopilot を承認する

計画を確認したら、実装に進みます。Autopilot を使うと、Copilot は完了したと判断するまで問題に取り組みます。

1. **Accept plan and build on autopilot (recommended)**、または使用中のバージョンで同様の名前のオプションを選択します。
2. プロンプトの下に **Autopilot** と表示されていることを確認します。
3. Copilot が計画に沿って反復し、コードを生成してテストを実行する様子を確認します。

> [!NOTE]
> 承認するとすぐに実装が始まることがあります。必ず計画を先に確認してください。依存関係が不足している、またはポートが競合していると報告された場合は、チェック完了とみなす前に環境の問題を解決してください。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同様にマージ前にレビューします。コードを確認し、サイトを実行して動作も確かめます。

1. <kbd>Shift</kbd>+<kbd>Tab</kbd> を押して Interactive モードに切り替え、**Plan** または **Autopilot** ではないことを確認します。
2. `/diff` を入力し、フィルターの実装とテストを確認します。
3. issue と計画時の決定に照らして結果を確認します。
4. レビューが終わったら <kbd>Esc</kbd> を押して差分表示を閉じます。
5. プロジェクトのチェック結果を確認し、失敗があれば Copilot に修正を依頼します。

## 新機能を確認する

コードが良さそうでも、実際に実行できるか確認します。前と同じようにアプリを起動し、Codespaces でポート転送されたサイトを開きます。

1. 次のプロンプトでアプリの起動を依頼します。

   ```plaintext
   ブラウザーでフィルター機能を試せるようアプリを起動してください。URL を教えて、サーバーは実行したままにしてください。
   ```

2. Codespaces でポート `4321` が利用可能になったら **Open in Browser** を選択します。
3. 計画で合意したカテゴリと発行元のフィルター、および組み合わせを試します。
4. リセットと結果がない場合の動作が issue と決定内容に合っていることを確認します。
5. Codespace に戻り、起動した開発サーバーを停止するよう Copilot に依頼します。

## まとめと次のステップ

会話モードを使い分けて、機能を構築しレビューしました。このレッスンでは次のことを行いました。

- GitHub issue から Copilot の会話を開始しました。
- Plan モードで要件を定義しました。
- Autopilot モードで機能を実装しました。
- コードをレビューしました。
- 転送したブラウザーで手動で機能を検証しました。
